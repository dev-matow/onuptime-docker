# Importing from Uptime Kuma

**31 of Uptime Kuma's 31 monitor types import today.** Every one of
Kuma's 111 `monitor` columns is classified below, and nothing leaves
Kuma without a line in the import report saying what became of it.
That guarantee is the point of the feature, and it is what the test
suite proves.

Eighteen of those thirty-one did not import in 1.12.0, and the reason
they do now is that Vigil grew the check types, not that the importer
learned to guess. The table below says what changes for each.

**A type having an equivalent is not a promise that every monitor of
that type imports.** The type decides which Vigil check is built; the
row decides whether Vigil's own rules accept it. Of the pinned
fixture's 31 monitors, one of every type, written by Kuma itself,
**27 of the fixture's 31 monitors import** and four are refused:

| Monitor        | Why it is refused                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `seed-http`    | Watches `http://127.0.0.1:3001/`. Vigil's target schema demands a hostname, an SSRF boundary, not a formatting preference. It also POSTs; see below.    |
| `seed-keyword` | Watches `http://127.0.0.1:9/`, same rule.                                                                                                               |
| `seed-docker`  | Reaches its daemon over a unix socket, so Kuma's host record has no hostname for Vigil's target to name. A host reached over `tcp://` imports fine.     |
| `seed-kafka`   | Authenticates with SCRAM-SHA-256; Vigil's Kafka check speaks SASL/PLAIN. An imported monitor could never authenticate, and would report a false outage. |

Those four are the honest shape of this feature: rules that exist for a
reason, refusing rows for that reason, and saying so on the report.
None of them is fixed by weakening the rule.

## The version this is written against

|           |                                                   |
| --------- | ------------------------------------------------- |
| Release   | `2.4.0`                                           |
| Commit    | `9f3b837c8c7f359ec1acee80b3c0430451986a03`        |
| Published | 2026-05-31                                        |
| Image     | `louislam/uptime-kuma:2.4.0`                      |
| Schema    | `database_version = 10`, 111 columns on `monitor` |

Not `master`. Kuma's `monitor` table is not a published interface. It
is 111 columns accreted across 50 knex migrations, several reused by a
later type for an unrelated purpose. `radius_password` holds an SNMP
community string. `radius_username` holds an Oracle login. Nothing in
the schema says so; you learn it by reading the release you targeted,
which is why one release is targeted and named.

The constants live in `src/modules/importers/kuma/pinned.ts` and are
asserted against a real Kuma database in
`tests/fixtures/kuma/kuma-2.4.0.db`: a file Uptime Kuma itself created,
migrated and wrote every row of. A Kuma release that changes the schema
version, the column count or the type list fails a test rather than
quietly publishing a wrong number here.

## How the 31 is counted

31 is the number of entries in the 2.4.0 tag's top-level monitor-type
selector (`src/pages/EditMonitor.vue`), **including Group and Manual**.
Excluding those two (neither describes a probe). Gives 29, which is the
denominator Kuma's own comparison tables use.

Three of the 31 are conditional in Kuma's UI and appear only on certain
hosts: `system-service` (Linux/Windows, not in a container),
`sip-options` and `tailscale-ping` (not in a container). They are
counted because they are values Kuma stores in `monitor.type`, and the
fixture contains one of each.

The set is identical to 2.3.2's, verified by diffing the two tags.

Two Vigil check types have no Kuma source at all: `tls-expiry` and
`domain-expiry`. Kuma expresses both as flags on an HTTP monitor
(`expiry_notification`, `domain_expiry_notification`) rather than as
checks of their own. The TLS flag maps onto Vigil's `tlsCheck`; the
domain flag has no home, and the importer will not invent a second
monitor to give it one. If you relied on Kuma's domain-expiry warnings,
create `domain-expiry` monitors after the import. The report tells you
which monitors had the flag set.

## What comes across on a monitor that does import

Carried: name, interval, timeout, active/paused state, group
membership, target host or URL, port, HTTP method (GET and HEAD), body
keyword and its inversion, JSON path and expected value, DNS record
type, Docker container and daemon address, database connection details,
MQTT/RabbitMQ/RADIUS/SNMP credentials, Redis password, gRPC service and
TLS setting, WebSocket subprotocol, Kafka topic and message, Globalping
location, systemd unit name, game-server protocol, the manual status an
operator declared, and the certificate-expiry warning.

Restated rather than copied:

- **Retries become time.** Kuma goes down after `maxretries` retries
  spaced `retry_interval` apart. Vigil asks how long a monitor has been
  failing, so the imported `failureWindowSeconds` is their product,
  the same wall-clock tolerance the operator actually chose.
- **Timeout** moves from seconds to milliseconds and is clamped to
  Vigil's 1000-30000ms. A Kuma timeout of `0` means none was ever
  stored, and Vigil's default applies.
- **Accepted status codes.** Kuma holds a JSON array of codes and
  ranges; Vigil holds one exact code, or none (in which case any 2xx or
  3xx passes). `["200-299"]` maps to none and loses nothing. A lone
  exact code is carried. Anything else. `["200-299","301","418"]`.
  Cannot be expressed, and the monitor's report line says so.
- **JSONPath becomes a dotted path.** `$.status.state` imports as
  `status.state`. Wildcards, recursive descent and filter expressions
  name more than one location, so those monitors are refused rather
  than narrowed to a meaning nobody wrote.
- **DNS and SNMP conditions.** Two shapes map: a single
  `record contains "x"` on a DNS monitor and a single `oid == "x"` on
  an SNMP one, each of which is what that type's `expectedValue`
  already means. Every other expression tree is counted in the report
  and dropped.
- **Connection strings.** PostgreSQL keeps its whole connection string,
  because that is Vigil's target too. MySQL and MongoDB are split into
  host and port. Vigil reads the pre-authentication handshake, so the
  credentials have nowhere to go. Redis is split as well, and its
  password is lifted into the config as a declared secret. SQL Server's
  ADO string is rewritten as the `sqlserver://` URL Vigil takes,
  credentials included; Oracle's Easy Connect string becomes an
  `oracle://` URL with the credentials **removed**, because that check
  asks the listener and never signs in.
- **Kuma's reused columns.** `radius_password` is three settings in one
  column. On a RADIUS monitor it is the test account's password, on an
  SNMP v1/v2c monitor it is the community string, and on an Oracle
  monitor it is a login Vigil never sends. Each lands somewhere
  different, and the report says which.

## Limitations that will bite

These are the ones worth knowing before you start, because they refuse
monitors whose type is otherwise fully supported.

1. **A URL with a bare IP address is refused.** Vigil's target schema
   demands a hostname. `http://192.168.1.10/health` is a monitor Kuma
   is happy with and Vigil will not store. The rule is an SSRF
   boundary, not a formatting preference. Give the host a name in DNS
   before importing, or recreate those monitors by hand.
2. **Only GET and HEAD import.** A Kuma monitor that POSTs is refused
   rather than downgraded: a GET against an endpoint expecting POST is
   a different check, and importing it would manufacture an outage.
3. **A Docker host on a local socket may have no importable target.**
   Vigil's Docker check targets the machine whose daemon is asked, and
   that field wants a hostname. A Kuma Docker host named `local` over
   `/var/run/docker.sock` has none, so the monitor is refused. A host
   reached over `tcp://` imports fine.
4. **A Kafka cluster on anything but SASL/PLAIN is refused.** Vigil's
   Kafka check speaks PLAIN and no other mechanism. Carrying SCRAM or
   GSSAPI credentials as PLAIN would create a monitor that can never
   authenticate, a permanent outage that is not one.
5. **A game Vigil cannot place is refused.** GameDig knows hundreds of
   titles; Vigil speaks three query protocols, and almost every title
   is one of the three under another name. A `game` id the importer
   cannot resolve to Source/GoldSrc, Minecraft or id Tech 3 is named
   and refused rather than queried with the wrong packet, which looks
   exactly like a server that is down.

Nothing is guessed around any of these. A refused monitor is `skipped`
in the report, with every reason it was refused, not just the first,
so fixing one does not reveal another on the next run.

## What else comes across, and what does not

The importer creates monitors, groups and status pages. Everything
below is a relationship Kuma stores, and each one either travels or
gets its own report line, never a silent drop.

| Kuma record                     | What happens                                                                                                                                                                                                                                                                                  |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Monitor groups (`parent`)       | **Carried.** A Kuma group becomes a Vigil group monitor and each child's `parentId` names it. Groups are created before their members. A child whose group was refused imports without one, and its line says which group it lost.                                                            |
| Paused state, retries, timeouts | **Carried.** See the section above for the two that are restated rather than copied.                                                                                                                                                                                                          |
| Secrets                         | **Carried** wherever the target type declares a field for one, and masked in the report by `redactConfig`.                                                                                                                                                                                    |
| Status pages                    | **Carried.** Slug, title, published state and the "powered by" line. A slug that is not a legal Vigil slug is rewritten; one already taken is suffixed; both changes are reported with the new URL.                                                                                           |
| Status page password            | **Not carried, and the page is imported private.** Kuma hashes with bcrypt and Vigil with scrypt, so neither can produce the other without the plaintext. A page behind a password must never become a public one by accident.                                                                |
| Status page public groups       | **Flattened.** Vigil's page holds one ordered list rather than named sections; the monitors are added in their Kuma order and each section gets a line naming what was lost.                                                                                                                  |
| Push heartbeat history          | **The last beat is carried** for an imported push monitor, so it arrives knowing when the job last reported in rather than knowing nothing. Everything before it stays in Kuma, see below.                                                                                                    |
| Notification providers          | **Not carried.** No provider credential is copied out of a Kuma database, or even read. Vigil has channels of its own for the same services ([NOTIFICATIONS.md](NOTIFICATIONS.md)); recreate the channel under Settings → Notifications and the imported monitors use it.                     |
| Monitor-notification links      | **Not carried.** A Vigil channel names the monitors it cares about, and a commercial routing policy is assigned to the workspace, a service or one monitor. Both are the destination's own configuration rather than the monitor's, so there is no attachment on an imported row to recreate. |
| Tags and tag applications       | **Not carried.** Vigil has no monitor tags. A group is the nearest thing and is not the same thing.                                                                                                                                                                                           |
| Maintenance windows             | **Not carried.** Vigil has windows of its own in the commercial edition (`docs/MAINTENANCE.md`) and Core has none, but neither is imported: **until you declare them again, imported monitors will alert during a window Kuma would have suppressed.**                                        |
| Heartbeats and statistics       | **Not carried**, beyond the last push beat. Vigil's uptime is duration-weighted over observations it made itself and hashed into its own ledger; importing another system's beats would put unverifiable rows in a chain whose whole purpose is that every row is verifiable.                 |
| Proxies                         | **Not carried.** Vigil probes targets directly. The proxy's credentials are never read from the source at all.                                                                                                                                                                                |
| Docker hosts, remote browsers   | **Flattened.** Vigil has no host or renderer registry, so the daemon address and the service URL are copied onto each monitor that used them.                                                                                                                                                 |
| API keys, users, incidents      | **Not carried.** Kuma's own accounts and history.                                                                                                                                                                                                                                             |

## Running it

**Settings → Import**, in two clicks. Choose your `kuma.db`, and Vigil
answers with a summary of everything it will do; confirm, and it does
exactly that.

The summary is not an estimate. It is a **real import that was rolled
back**: every monitor built, validated and inserted, every database
constraint actually checked, then the whole transaction abandoned. That
is why it can tell you a slug is taken or a push token is already in
use. An estimate could not. The file is hashed on the way in and the
hash is checked on confirm, so the second click applies the run you
were shown and not a different file.

The import itself is one transaction. Either the organization has the
monitors or it does not; a migration that half-succeeds leaves you
reconciling two systems by hand at exactly the moment you were trying
to stop doing that.

`importKumaFile(db, actor, path)` is the same thing without a browser,
for a database too large to upload.

## Point it at a copy

The reader opens `kuma.db` read-only and never writes a byte of it. That
is as far as the guarantee goes: SQLite still touches the `-shm` index
beside a WAL-mode database in order to read it, and a source on a
read-only filesystem will refuse to open at all for the same reason.
Copy the file out of your Kuma volume and import the copy. It costs
nothing and removes the question.

Checkpoint it first if Kuma is still running:
`sqlite3 kuma.db "PRAGMA wal_checkpoint(TRUNCATE);"`. Everything Kuma
has written since the last checkpoint lives in the `-wal` sidecar, and
an upload carries one file.

## The import report

Every import returns a report rather than writing one to the database.
Nothing is persisted: there is no import log in the schema, so adopting
this feature costs no migration. Each source record gets one entry:

| Outcome       | Monitor created | Meaning                                                                    |
| ------------- | --------------- | -------------------------------------------------------------------------- |
| `imported`    | yes             | Nothing changed on the way across.                                         |
| `transformed` | yes             | It exists, and it means something slightly different. The entry says what. |
| `skipped`     | no              | Vigil maps the type, but not this row. Usually fixable.                    |
| `unsupported` | no              | Vigil has nothing to map it to. Not fixable by editing.                    |

A report also carries a status: `completed`, `refused` (nothing was
written, see the next section) or `preview` (nothing was written
because you asked what would happen). A preview's monitor ids name rows
that were rolled back; the status is how a caller knows not to follow
them.

Secrets never appear in it. A config carried into an imported monitor is
shown through `redactConfig`, so an MQTT or Redis password reads as the
mask sentinel. The report is rendered, and a rendered password is the
same leak the monitor page closes.

## A database from a newer Kuma

The importer refuses it, and reports why: the schema version it found,
any column it has never classified, any monitor type with no matrix
entry. Nothing is written; the transaction never opens.

That is deliberate. A column whose meaning moved produces monitors that
_look_ right, which is the one failure nobody catches. A caller that
understands the risk can pass `allowSchemaDrift: true`, and the drift
stays on the report either way.

## Refreshing the pin

1. Diff the new tag's `src/pages/EditMonitor.vue` type selector against
   the table above. If the set changed, every number on this page
   changes with it.
2. Re-run `tests/fixtures/kuma/seed-kuma.mjs` against the new image,
   see that directory's README.
3. Update `src/modules/importers/kuma/pinned.ts` and the matrices. The
   tests assert the pin against the fixture and the matrices against
   both, so a stale pin fails loudly instead of publishing a wrong
   version number here.
